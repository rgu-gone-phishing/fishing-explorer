# Fishing Explorer

Exploratory design for a local research interface built on Global Fishing Watch (GFW) data, with explicit resolution controls, reproducible historical extracts and offline access to saved studies.

Start with the **value-add parity phase** draft, prepared on 23 October 2026:

- [Product specification](docs/parity-phase-specification.md): scope, user workflows, data semantics and acceptance criteria.
- [Development plan and backlog](docs/parity-phase-development-plan.md): architecture, discovery gates, ordered work, four-week checkpoint and verification.
- [GFW evidence and design critique](docs/gfw-parity-evidence.md): current documentation, pinned source references, existing strengths and unresolved constraints.
- [Visual screen concepts](docs/parity-phase-concepts.md): extraction, historical-job recovery and VMS availability.

Phase one targets clearer access to authorized GFW capabilities; phase two explores additional analytical methods. VMS is a high-priority access investigation, with country-specific exports and permissions to establish before promising integration.

**Data & methods → Explore country access** provides a dated VMS publication/commitment inventory and product-specific evidence histories. Record view, automated-query, download, local-retention, transformation and redistribution evidence independently. Unknown stays distinct from allowed or denied. A representative CSV can be inspected locally for its checksum, column names and text formats; data rows and the original file are not retained. This is schema discovery, **not an analytical VMS import adapter**. Immutable evidence histories can be exported/imported separately from observations. Country-specific export eligibility and an authorized representative sample remain prerequisites for verifying an import adapter. The client has confirmed academic/non-commercial nonprofit use; explicit VMS provider authorization is unknown and is an item for the next meeting. Nonprofit status does not establish product-specific permission.

**Data & methods → Local diagnostics & storage** shows runtime/configuration presence, available volume space, operation states and dated quota headers observed during normal GFW requests. The explicit connectivity button checks one pinned public metadata response; it does not establish access to every product. Quota observations may lag and are not a live remaining-call meter. Workspace scans inventory logical file sizes and optionally verify recognized records/archives. Links are skipped, active writes and limits remain explicit, and no research file is repaired or deleted. The optional write/read check creates and removes only its own temporary probe.

Use **Prepare diagnostic export preview** to review a fixed support-file snapshot before downloading it. It contains aggregate operational facts and safe codes, with no token, request/response bodies, research geometry, study/vessel names, filenames, environment values or raw stacks. Filenames remain in the local findings view. Nothing is sent automatically. Safe request observations are stored locally in a bounded `health-log.json`; invalid pre-existing files are preserved. If the web app cannot start, run `node scripts/diagnose.mjs PATH_TO_EXISTING_DATA_DIRECTORY` for a read-only, redacted inventory on stdout. Add `--write-test` only to test temporary write/read access. This command makes no network request and does not load or modify saved job states.

The earlier [API feasibility study and extraction playbook](docs/gfw-api-feasibility.md) preserves the 9 October 2026 research direction and small v4 authenticated probes. Its dated observations are useful evidence, not a current v5 capability guarantee.

A local upstream frontend checkout is ignored by Git. Its revision and reproduction instructions are in [references/README.md](references/README.md).

## Build a local preview package

Run `npm run package` to create a versioned ZIP and external SHA-256 file in ignored `dist/`. The package contains a reviewed runtime allowlist, bundled map assets and licenses, an offline setup guide, and a generated synthetic example. No npm install or build is required on the receiving machine; an approved Node.js 22+ runtime is required.

Extract the entire ZIP into a new folder and open `README.html`. Use its `start.cmd` on Windows or `sh start.sh` on Linux/macOS; the direct equivalent is `node scripts/launch.mjs`. The packaged launcher verifies listed application files before startup and defaults to a separate per-user data directory. Pass `--data-dir` to select an existing workspace outside the application folder, and `--port 0` to allocate an available loopback port. The source checkout commands below keep their existing `local-data/` default.

The package includes offline diagnostics, explicit proxy/CA guidance and backup/update/removal instructions. Checksums establish consistency, not publisher authenticity. Linux cold-start, restart and browser workflows have been checked; the representative Windows/Intune and managed-network pilot remains open. [Offline setup guide](distribution/README.html) · [Verified package preview](docs/assets/local-release-preview.png).

## Run the local application

Requires Node.js 22 or later (tested here with Node 24.15). No package installation or build is needed:

```sh
npm start
```

Alternatively run `node server/index.mjs`, or use `start.cmd` on Windows. Open the one-time local launch link printed in the terminal. It establishes an HttpOnly local session and removes the bootstrap token from the address bar. Keep that launch link private. Stop with Ctrl+C; restart and use the new link to reopen saved extracts.

The app offers a map-based area builder with bounding boxes, polygon drawing and GeoJSON import, exact UTC dates, spatial/time aggregation controls, saved extract tables/charts, portable JSON bundles containing CSV, query, boundary, caveats and checksum manifests, and saved comparisons with compatibility checks, paired maps and explicit normalization. Choose a clearly labelled synthetic fixture, or connect your personal GFW API token in **Data & methods** and select **GFW · AIS apparent fishing activity**, **AIS vessel presence**, or **SAR vessel detections**. Source-specific grouping, filters, date coverage and units are shown explicitly. The token stays in server memory, is never included in an export, and is cleared on restart/disconnect. Live requests transmit the selected query geometry to GFW and consume API quota. The server does not automatically read `api-secret.txt`.

**Find saved or retrieve →** checks the indexed local library before submitting new work. Compatible archived extracts and fully saved historical windows are offered with their source dates, verification status and caveats. Choosing one opens the requested window locally without changing the builder or creating another extraction. If the entire search finishes with no compatible result and no verification issue, the original Run action continues to fresh retrieval. With matches, unreadable sources or unchecked pages, choose saved data, continue checking, or explicitly request a fresh result. **Check compatible saved data** performs only the local check and never starts retrieval automatically.

Reuse requires the same source/version, units, exact geometry, named-boundary identity/version, grid, time grain, grouping and filters. Dates may select complete saved bins inside a larger source window; whole-period values cannot be split. The chosen source is rechecked before use, and a changed builder draft invalidates the choice. A parent batch can remain partial outside a fully retrieved selected window, which stays clearly labelled. Saved scopes are not guarantees of current API values or publisher authenticity. Static-release and VMS import adapters remain separate work. [Synthetic reuse preview](docs/assets/saved-reuse-preview.png) shows a compatible result and a rejected grid mismatch.

Data is stored in ignored `local-data/` by default. Set `FISHING_EXPLORER_DATA_DIR` to choose a workspace and `FISHING_EXPLORER_PORT` to change port 4310. One server may own a workspace at a time. Interrupted live jobs are marked recovery-needed. Use **Check GFW last report** with the same account, review any candidate, or explicitly close the unresolved local job after reviewing remote activity. Ambiguous results require manual ownership confirmation, recorded in provenance and caveats; they are never automatically adopted. Retrying creates a new linked job. Stopping locally does not cancel GFW processing. Saved artifacts are integrity-checked before viewing/export and can be reimported through Saved extracts.

For an unresolved live report, **Check automatically · up to 15 min** performs at most 12 checks of the existing last-report endpoint. Delays increase from 15 seconds with jitter, and provider `Retry-After` waits take precedence. It never resubmits a report or accepts a candidate automatically. Use **Stop automatic checks** to stop locally. Checks also stop on a candidate, access/schema/ownership mismatch, budget exhaustion, credential change, shutdown or restart; resuming is explicit. A recovered candidate must be opened and reviewed before acceptance, and a changed payload, query or check time invalidates an earlier review. The original job remains unresolved until you accept the reviewed result or deliberately close it. Provider-requested waits also apply to manually retrying a rate-limited job.

Current application limits: 31 days for synthetic generation, 366 days for live reports, 32 MiB provider responses, 40 MiB JSON bundle imports and 256 MiB documented extract ZIP imports (compressed and expanded sizes). Historical batches support reviewed calendar-month partitions, sequential retrieval and restart-safe completed chunks. ZIP exports stream individual files; each provider response is still parsed within the 32 MiB per-chunk limit. Imported/drawn areas support up to 250,000 vertices, 2,000 polygon parts and 4,000 rings, with holes; boundary files and query/study requests are limited to 16 MiB. Antimeridian crossings and latitudes outside ±85° are rejected explicitly. These are client implementation limits, not claims about GFW's maximum capacity. Geometry validation uses a spatial index and bounded work; difficult geometries can be rejected without modifying their coordinates.

In **Saved extracts → Inspect extract**, **Download documented ZIP** packages the original bundle and embedded files with a field dictionary, readable query summary, exact boundary, citations and use conditions. **Review handoff summary and data dictionary** previews those documents locally. `manifest.json` remains the original manifest; `package-manifest.json` records each packaged member's checksum. `spreadsheet-data.csv` is a separate formula-protected derivative, while original `data.csv`, JSON values and provider responses remain unchanged. Import numeric-looking identifiers as text to preserve leading zeros. Reopen the ZIP through the individual-extract importer with no token or upstream request. Unsupported documentation versions fail explicitly. The importer retains the verified artifact; a later package is newly generated, so its container/source-JSON formatting may differ while original embedded files and their hashes remain intact. [Synthetic documented ZIP](docs/assets/extract-handoff-example.zip) demonstrates the handoff.

New historical ZIPs use manifest version 3 and add a root dictionary, query summary, exact query/boundary, citations and use conditions. The summary lists each partition, provider version and missing window. CSV files remain original chunk derivatives; consult their manifests for the CSV transformation used. Imported version 1/2/3 archives remain byte-for-byte recoverable; re-exporting an old ZIP does not add documents or change its contents.

In **Saved extracts → Inspect extract**, apply a saved-data window, optional exact original time label and exact group to explore locally. The map, time series, grouped subtotals, raw-row table, figures and GIS export use that same applied selection. Every requested bin is reachable through chart pagination; missing bins are hatched and explicit zeros stay zero. Group shares use the entire selected measure total, with the denominator stated. Group search only narrows the summary table. Monthly windows preserve calendar boundaries and partial original endpoints; whole-period values cannot be split into finer dates.

Use **Export applied view · ZIP** for selected JSON/CSV rows, complete selected time-series/group tables, provenance, original source bundle and caveats. It exports all selected data, not just visible pages. The original source ZIP remains unchanged and complete. A derived-view ZIP is not an input to the original-extract ZIP importer; transfer the original source ZIP and study plan when reopening the same view elsewhere. Studies retain the applied selection and saved-map viewport against the exact linked source hash. Apply/reset draft filters and link the source before saving a data-view study. [Synthetic selected-view package](docs/assets/saved-view-example.zip), [HTML report](docs/assets/saved-view-example.html), [controls](docs/assets/saved-view-controls.png) and [missing/zero preview](docs/assets/saved-view-series.png) demonstrate the workflow.

In **Saved extracts → Inspect extract**, use **Save SVG figure** or **Save printable HTML summary**. Exports follow the applied window/time-label/group selection and preserve source/version, units, query/data/boundary hashes, recovery warnings and caveats. Maps use returned-coordinate symbols and a dynamic scale; time charts distinguish missing bins from explicit zeros. The offline HTML includes all selected group and time-bin totals and can be printed through the browser. No scripts, external assets, API requests or extra packages are needed. Keep the original research bundle alongside the report for full data and exact geometry. [Synthetic example report](docs/assets/extract-report-example.html), [SVG figure](docs/assets/extract-report-example.svg) and [reproducible source bundle](docs/assets/extract-report-example.bundle.json) illustrate the workflow.

For GIS, open **Export GeoTIFF for GIS** on a saved extract and choose **Review GIS export** after applying the saved-data window and time/group filters. The local export writes a north-up EPSG:4326 raster with one Float64 band, NaN nodata and preserved numeric zeros. It sums the selected returned records at each grid centre; it does not interpolate, convert to density or fractionally clip edge cells. A populated pixel does not imply full temporal/group coverage. The review shows units, dimensions, actual raster extent and any small coordinate alignment adjustment. Changing the selection invalidates the reviewed download.

The GIS ZIP contains the TIFF, raster dictionary/manifest, original source bundle, exact query/boundary, citations and use conditions. Its manifest records parent and implementation hashes. Keep the package together; this GIS ZIP is distinct from the documented-extract import format. Limits are one million returned coordinate tuples, four million output pixels and a 256 MiB package. Empty, off-grid or oversized outputs are rejected without coarsening. [Synthetic GIS package](docs/assets/geotiff-example.zip) and [review preview](docs/assets/geotiff-preview.png) show the workflow. GDAL interoperability checks passed for synthetic and saved live AIS data, plus handcrafted 0.01° presence/SAR cases; see implementation status for the precise evidence scope. Normal startup/export still needs only Node, not GDAL or Python.

Use **Studies & layers** to save immutable workspace revisions, link completed results, and import local GeoJSON/CSV reference layers. The last saved/opened study restores at startup without a GFW request. Study-plan exports contain query/view settings and reference checksums; move data bundles and layer backups separately. Layer citations, validity and use conditions remain visible and travel with backups. Reference overlays never replace the analysis boundary automatically.

Use **Show / refresh live preview** to explore AIS activity, vessel presence or SAR image tiles for the chosen source, version, dates and filters. Preview spatial detail, time interval and opacity are separate from saved report resolution. Panning and zooming while the preview is active sends tile requests to GFW; changing source, dates or filters stops it until explicitly refreshed. Unavailable tiles are hatched and never interpreted as zero activity. Preview images use adaptive provider scales and are not quantitative exports. Sessions expire after 30 minutes and are not restored automatically with a study. Saved maps remain usable offline.

Expand **Choose a named EEZ, protected area or fisheries region** to load a GFW catalogue, search its saved names/IDs/ISO codes, and retrieve a boundary snapshot. Names may repeat; selection uses dataset plus ID. **Use this analysis boundary** applies compatible geometry explicitly. Snapshots and source backups reopen/import offline. Queries and extract bundles retain the actual selected geometry, source identity, supplied version or unknown status, retrieval time and hashes. Editing bounds or drawing/importing another area clears the named-source association. Large, polar or antimeridian boundaries remain limited by the current validator; they are retained for inspection rather than replaced with a bounding box. Optional provider simplification parameters are experimental: their units and tolerance semantics are unverified, and they are not saved-grid resolution.

Use **Vessels & events** to search by name, MMSI, IMO or callsign, select a historical AIS identity, inspect reported/registry/model evidence, and fetch events for a chosen overlap window. Search cursors and event offsets are handled separately; use the explicit next-page or fetch-remaining controls. Snapshots retain raw pages and can reopen without a GFW token. Port-visit levels are evidence categories, not probabilities; event maps are not vessel tracks.

Use **Vessels & events → Explore events in a study area** to copy the extract builder’s boundary and dates, then choose an event product, pinned version, flags/classes, optional AIS IDs, evidence levels and whole-event duration bounds. Copying stays local; **Retrieve area events** explicitly sends the selected geometry to GFW. The saved area remains separate from subsequent builder edits. Results preserve full event dates and source positions, show the submitted boundary, and support paginated inspection, explicit identity retrieval and a local return to the saved area. Event positions are summaries, not tracks; elapsed event hours are not gridded fishing hours. Area lookups use the existing offline lookup archives/study references and a 366-day query limit. The recorded POST body can be reconstructed from its hashed parameters and the exact query geometry.

The area panel's **Area result type → Provider statistics** requests GFW's aggregate event/vessel/flag counters, time series and grouped counts for the same saved selection. Choose hourly/daily/monthly/yearly bins, grouping and requested sections explicitly. **Time matching** supports overlapping events or events starting in the window, for both records and statistics. Provider totals are separate from loaded-page counts; source time-bin totals may differ, and distinct/group counts are not automatically additive. Missing fields and empty series are not filled with zeros. Statistics, raw responses and compact request provenance export/import through the lookup archive workflow and can be attached to studies.

In **Vessels & events**, switch **Search mode → Advanced identity fields** to combine names, recorded MMSI/IMO/callsign values, AIS IDs, flags, GFW vessel/gear classes, registry gears, owner-name text and identity-record date bounds. Choose AIS, registry or combined scope for identity fields. Lists use OR within each field; different fields use AND. The generated query is inspectable, and saved results retain the provider's interpreted query, match criteria and requested ownership/authorization evidence. Historical periods are not fishing-activity windows; criteria may match different records in one result. Filters are never silently dropped, and old basic-search archives remain readable. Names/owners accept plain text rather than arbitrary wildcard or SQL expressions. Source evidence can be absent, unsupported or an explicit empty list; these states are not treated as a compliance finding.

Use **Vessels & events → Local vessel sets & annotations** to save research selections. Add an AIS identity from a saved search or identity record, or enter a manually cited identity. Each ID/version pair remains separate; labels and annotations are user supplied. Saving appends an immutable revision, and removing a draft member does not alter older revisions. Source-linked members retain the original lookup ID and checksum; exact source archives can be reopened offline or imported separately. Set-history backups preserve revisions and accept matching-prefix extensions while rejecting conflicting histories. Studies can retain and restore an exact set revision. Limits: 500 members per revision, 100 revisions and 16 MiB per history; these sets do not automatically filter gridded reports or aggregate multiple vessels.

Select an AIS identity to use **Provider vessel insights**, choose its requested UTC period and categories, and retrieve source-defined coverage, fishing, gap and reported IUU-list indicators. Missing/unsupported fields remain unavailable; zeros are preserved. Returned source datasets, raw responses and caveats travel with the saved lookup. Additional flag-history and MOU-list categories may require extra account access; a denial does not silently drop categories or trigger another request. Associated event references can retrieve their whole event when a supported source dataset/version is supplied. Exact insights end-date inclusion remains unverified. Insight and event-detail snapshots use the same offline lookup import/export and study references.

Use **Import a vessel/event lookup archive** to reopen an exported lookup locally. Import verifies the query, request URLs, page hashes, cursor chain, normalized records and completeness claims. Exact duplicates reuse the existing archive; differing content with the same original ID receives a separate local ID. Imported archives remain immutable. **Copy for continued retrieval** creates a linked working copy without fetching; subsequent page retrieval is explicit. Portable study references can reconnect to an imported lookup only when its original identity and content checksum match. Lookup imports are capped at 128 MiB, with the existing 100-page / 32 MiB raw-page limits.

Use **Infrastructure** to review tile requests for the builder's area, retrieve GFW's pinned filtered infrastructure product, and inspect predicted oil-related, wind-related or unknown structures. Confidence categories and incomplete detection dates remain explicit. Date filters operate on saved first/last detection spans; they can change without downloading tiles again. A supplied date boundary is respected even when the other date is missing. The snapshot can overlay workspace maps using its own displayed dates, and completed snapshots plus display settings can be linked to studies. Raw MVT/metadata backups reopen/import offline; filtered CSV and GeoJSON exports include all matching records. Missing tiles stay partial, and exact duplicates are removed while differing records for the same structure ID remain visible. This is the filtered map product, not the broader bulk-detection dataset or an authoritative installation register.

To retrieve longer periods, enable **Plan a historical batch**, choose a calendar-month chunk size, and review the exact windows before starting. Pause waits for the current chunk; resume preserves completed work and stops on unresolved upstream jobs. Complete and explicitly partial ZIP exports include CSV files, chunk bundles and a manifest. Plans are capped at 240 chunks, roughly 20 years, and ZIP data at 2 GiB. Size/duration estimates remain uncalibrated.

Use **Saved extracts → Import historical batch ZIP** to restore a complete or partial archive without a GFW token. Uploads stream to local staging; the batch becomes visible only after all entries, manifests, hashes, CSV copies and query windows pass validation. The original ZIP is retained byte-for-byte alongside verified bundles, so allow space for both. Exact duplicate ZIPs reuse the existing valid archive; differing versions stay separate. Imported batches are read-only. **Copy remaining retrieval plan** reuses completed chunks without requesting data; starting that copy is a separate action. If the source recorded attempted missing chunks, review upstream activity before confirming another submission. ZIP32 stored/Deflate imports support up to 2 GiB plus 128 MiB metadata, with 128 MiB per bundle/CSV; ZIP64 and encrypted archives are unsupported.

**Infrastructure → Bulk infrastructure detections** is an experimental, separate workflow for the less-filtered v1.1 bulk product. Review the builder's exact area and optional first/last structure-detection dates, label, confidence and structure-ID filters. Submit once, check its remote status explicitly, then save the three original source files. The local record survives restarts; uncertain submissions require recovery of the matching report ID instead of an automatic retry. Stopping a local transfer does not cancel GFW generation.

Bulk CSV downloads remain gzip-compressed on disk and stream through bounded gzip/UTF-8/CSV syntax checks. The preview is limited to the first 50 records and 2 MiB of text; it is not a complete map or a distinct-structure census. Export keeps original files, provider notes, query/provenance, hashes and a readable summary together. Importing that archive verifies its members offline and creates an immutable record. Complete records can be attached to studies and checked in workspace diagnostics. Limits are 512 MiB compressed data, 2 GiB expanded CSV and 600 MiB ZIP imports; allow extra disk space for staged upload and verified files. [Synthetic bulk archive](docs/assets/bulk-infrastructure-example.zip) and [preview](docs/assets/bulk-infrastructure-preview.png) illustrate the workflow. Live creation/status checks succeeded, but the provider test report remains pending, so actual file-transfer/schema verification is still open.

In **Saved extracts**, choose **Analyze entire batch** (or **Analyze saved chunks · PARTIAL**) for one map, time series and paginated table across the saved chunks. Display dates and an exact group filter affect only the local view. Monthly filters respect existing bin boundaries. Unretrieved windows, bins without returned rows and explicit zeros stay distinct; every row links to its original chunk bundle. Resuming retrieval invalidates the old view until you apply the filters again. The server verifies one chunk at a time, serves 50 rows per page, and omits maps above 20,000 coordinates until you narrow the selection; totals retain all selected rows.

A study can now retain the batch’s applied date window, exact group and map viewport. Open the batch view, apply its filters, then save a revision in **Studies & layers** with the batch selected under **Link saved results**. Paused partial batches with at least one completed chunk are eligible and labelled with their saved/total chunk count; they are not promoted to complete results. Unapplied filters, active retrieval or changed source content prevent saving an applied view. The study’s builder query remains separate from the batch’s original query.

Reopening or importing a study restores its historical view only against the original source checksum. If the native batch has since advanced, the old study reports a changed reference; an imported archive with the exact old content can restore that earlier view. A study-linked analysis continues checking the source identity while paging/applying filters. To deliberately inspect a changed batch, open it again from Saved extracts. Transfer its permitted complete/partial ZIP separately from the study plan. [Restored partial historical view](docs/assets/batch-study-preview.png).

Historical batch analysis also offers **Save batch SVG figure** and **Save batch HTML summary**, with **PARTIAL** in the labels and filenames when any retrieval window is missing. Apply display dates/group first: exports are tied to that reviewed batch fingerprint and reject changed/running batches. A fully retrieved selection inside an incomplete batch remains explicitly partial at batch level. Figures distinguish unretrieved windows, retrieved bins without rows and explicit zeros; summaries retain per-chunk source hashes, versions, caveats and missing windows. Original historical ZIPs remain the data handoff. [Synthetic partial-batch report](docs/assets/batch-report-example.html) and its [source ZIP](docs/assets/batch-report-example.zip) demonstrate these distinctions.

Batch plans store their common geometry once, with per-chunk dates, and reopen both earlier and compact storage formats. Exact coordinates and query identities are preserved. Detailed boundaries remain available in saved studies; the original 161,185-vertex ICCAT boundary has been verified through validation, map display, batch preview and offline study restoration without simplification.
