Fishing Explorer

Open saved research, choose data resolution and retain the query with the result.

No Docker, Python, compilation, global package install or service installation is needed. Use an existing runtime approved by your organization.

Start in three steps

  1. Extract the entire ZIP to a new folder. Do not run files from inside the ZIP viewer.
  2. On Windows, double-click start.cmd. On Linux or macOS, open a terminal in the extracted folder and run sh start.sh.
  3. Open the one-time local link printed in the terminal. Keep the terminal running while using the application. Stop it with Ctrl+C, and use the newly printed link after restarting.

The launcher checks the files listed in the release manifest, binds only to the local machine and prints the chosen data location. The launch link grants access to this local session: keep it private.

Try it offline

In Saved extracts, import examples/synthetic.bundle.json. It contains 28 illustrative rows over seven days. It is a fixture, not GFW observations or a prediction of fishing.

Retrieve data deliberately

Connect your personal GFW API token in Data & methods. In the builder, review the area, dates, source and saved detail, then use Find saved or retrieve. Existing compatible data is offered first.

Tokens stay in server memory and are cleared on restart/disconnection. No token file is read automatically. Live API requests send their selected geometry and filters to GFW and may consume quota.

Your data stays outside the application folder

SystemDefault data directory
Windows%LOCALAPPDATA%\FishingExplorer\data
macOS~/Library/Application Support/Fishing Explorer/data
Linux$XDG_DATA_HOME/fishing-explorer/data, or ~/.local/share/fishing-explorer/data

Choose another approved writable folder, including an existing Fishing Explorer workspace:

start.cmd --data-dir "D:\Research\Fishing Explorer data" --port 4311

sh start.sh --data-dir "/home/you/Research/Fishing Explorer data" --port 4311

The direct command is node scripts/launch.mjs with the same options. CLI arguments override FISHING_EXPLORER_DATA_DIR and FISHING_EXPLORER_PORT. Use port 0 to choose an available loopback port, or a port between 1024 and 65535. Keep the workspace outside the extracted application directory, including linked locations.

No migration or automatic copying of a developer checkout’s local-data/ occurs. Point --data-dir to that existing directory from a separately extracted application, or transfer verified bundles and study plans. One process can own a workspace at a time.

Saved queries, geometry, original data, study revisions, partial results and recovery candidates can be confidential. Stop all instances before copying the entire data folder for backup. Keep the source bundles with derived figures and selected-view exports.

Network and account access

Saved-data work and the bundled map context are available offline. Online retrieval requires access to gateway.api.globalfishingwatch.org over HTTPS. Experimental bulk downloads additionally use the documented report path under storage.googleapis.com/api-bulk-release-us-central1/. No CDN or remote basemap is needed for saved maps.

Have IT configure the approved proxy and CA settings. Browser access alone does not establish that Node’s transport has the same proxy configuration. Node’s environment-proxy support is version-dependent; the documented options below require a supporting runtime, such as Node 22.21+ on the 22 branch or 24.5+ on the 24 branch. See Node’s enterprise-network documentation and the 22.21 release notes.

node --use-env-proxy scripts/launch.mjs --data-dir "D:\Research\Fishing Explorer data"

Alternatively, IT can set NODE_USE_ENV_PROXY=1 before launching, along with the appropriate HTTP_PROXY/HTTPS_PROXY values. Keep loopback access available through the approved NO_PROXY configuration without discarding existing organization entries. Use NODE_EXTRA_CA_CERTS for an approved PEM CA file when required; do not disable TLS verification.

If organizational policy blocks Node, command files or loopback access, obtain approval from IT. The package does not change system policies or install an alternative runtime. Metadata connectivity checks do not prove permission for every dataset.

When startup fails

What you seeNext action
Node not found / too oldCheck node --version and ask IT for an approved Node 22+ runtime. This package contains no Node binary.
Package verification failedExtract a clean copy into a new application folder. Keep the separate data directory. Verification checks listed files, not publisher authenticity or unlisted additions.
Port already in useClose the other application instance or choose another local port with --port. The service does not bind to the LAN.
Data folder lockedClose its other application instance. If uncertain, ask for help checking the lock; do not remove a lock belonging to a running process.
Permission / disk-space errorChoose a writable location or free space outside the application’s data workflow. Preserve research files for diagnosis.

Offline inventory

node scripts/launch.mjs --diagnose --data-dir "D:\Research\Fishing Explorer data"

node scripts/launch.mjs --diagnose --data-dir "D:\Research\Fishing Explorer data" --write-test

Diagnostics inventory is offline: it does not start a server, load jobs, submit requests or acquire the workspace lock. The optional write test creates and removes only its own temporary probe. The output omits research content, credentials and private paths. It is an inventory, not a full data-integrity audit. Use the application’s explicit workspace verification for deeper checks.

For an application-file check, run node scripts/verify-release.mjs. It reports consistency with the included manifest. Obtain the ZIP and its external checksum from a trusted location; hashes are not a publisher signature.

Review diagnostic output before sharing it yourself. Do not include API tokens, signed URLs or the one-time launch link. No support report or telemetry is sent automatically.

Update, roll back or remove

  1. Stop the application and back up the complete data directory.
  2. Extract the new version into a new application folder and verify it. Retain the previous application folder until the new version and data open correctly.
  3. Launch the new version against the same external data directory. Review startup diagnostics and source integrity. Do not merge application files from different packages.

Raw source artifacts are not rewritten as part of this launcher. If a newer build writes a format an older build does not understand, use the pre-update data backup for rollback; do not assume older code can reinterpret new formats.

To remove the software, stop it and remove the extracted application folder after preserving any files you added there. The separate data directory remains. Remove research data only as a separate, deliberate decision after backup.

The source repository’s developer commands retain their existing behavior: npm start / node server/index.mjs default to its local local-data/. These release launchers instead use the separate per-user location above.
